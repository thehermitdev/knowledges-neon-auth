> สรุป: Managed Better Auth จัดเก็บผู้ใช้ เซสชัน และการตั้งค่าไว้ในสคีมา neon_auth ของฐานข้อมูล ดังนั้นข้อมูลการยืนยันตัวตนจึงถูก clone โดยอัตโนมัติเมื่อคุณสร้างบรานช์ ทำให้แต่ละบรานช์มีสภาพแวดล้อมการยืนยันตัวตนที่แยกออกจากกันอย่างสมบูรณ์ ใช้หน้านี้เมื่อคุณต้องการทดสอบ OAuth provider, การเปลี่ยนแปลงนโยบาย RBAC, โฟลว์การรีเซ็ตรหัสผ่าน หรือการ refactor แอปพลิเคชันครั้งใหญ่ได้อย่างปลอดภัยโดยไม่กระทบผู้ใช้ production แต่ละบรานช์จะมี Auth API URL เฉพาะของตัวเอง และเซสชันกับโทเค็นจะไม่สามารถใช้ข้ามบรานช์ได้

# การยืนยันตัวตนแบบแตกบรานช์

การยืนยันตัวตนทำงานร่วมกับบรานช์ฐานข้อมูล Neon อย่างไร

**หมายเหตุ: Beta**

**Managed Better Auth** อยู่ในสถานะ Beta คุณสามารถส่งความคิดเห็นผ่าน [Discord](https://discord.gg/92vNTzKDGp) หรือผ่าน [Neon Console](https://console.neon.tech/app/projects?modal=feedback)

การยืนยันตัวตนมักเป็นหนึ่งในส่วนของ application stack ที่ทดสอบได้ยากที่สุด ในสถาปัตยกรรมแบบดั้งเดิม ข้อมูล identity จะอยู่ในบริการ third-party แยกต่างหาก ขณะที่ข้อมูลธุรกิจของคุณอยู่ในฐานข้อมูล การแยกกันเช่นนี้ทำให้การสร้าง staging environment ที่สมจริง หรือการทดสอบการเปลี่ยนแปลงสิทธิ์โดยไม่กระทบผู้ใช้ production ทำได้ยาก

หนึ่งในคุณสมบัติเฉพาะของ Managed Better Auth คือการรองรับ [database branching](https://neon.com/docs/introduction/branching) โดยตรง เนื่องจากข้อมูลการยืนยันตัวตน (ผู้ใช้ เซสชัน และการตั้งค่า) อยู่ในสคีมา `neon_auth` ของฐานข้อมูลโดยตรง ข้อมูลเหล่านี้จึงถูก clone ไปพร้อมกับข้อมูลธุรกิจเมื่อคุณสร้างบรานช์

ผลลัพธ์คือแต่ละบรานช์จะมีสภาพแวดล้อมการยืนยันตัวตนที่แยกออกจากกัน ทำให้สามารถทดสอบการเปลี่ยนแปลงสิทธิ์ OAuth provider ใหม่ หรือการ refactor แอปพลิเคชันครั้งใหญ่ได้อย่างปลอดภัย

**ข้อมูล:** Managed Better Auth branching รองรับผ่าน API เช่นกัน ดูชุด REST API endpoint ทั้งหมดได้ที่ [เอกสารอ้างอิง Managed Better Auth API](https://neon.com/docs/reference/api/auth/get-neon-auth)

## วิธีการทำงาน

เมื่อคุณสร้าง [database branch](https://neon.com/docs/introduction/branching) คุณจะได้รับสำเนาที่เหมือนกันของข้อมูลการยืนยันตัวตนทั้งหมดจาก parent branch ณ เวลาที่สร้างบรานช์:

```
Production (main)                Preview Branch (preview-pr-123)
├── Users                   →    ├── Users (copied at branch time)
├── Sessions                →    ├── Sessions (copied, but will expire)
├── Configuration           →    ├── Configuration (independent copy)
├── OAuth providers         →    ├── OAuth providers (same credentials)
├── JWKS keys               →    ├── JWKS keys (copied)
└── Organizations           →    └── Organizations (copied)
```

หลังจากแตกบรานช์แล้ว สภาพแวดล้อมแต่ละชุดจะทำงานแยกจากกัน:

1. **การแยกข้อมูล:** การเปลี่ยนแปลงในบรานช์หนึ่งจะไม่ส่งผลต่อบรานช์อื่น การสร้างผู้ใช้ใน preview branch จะไม่สร้างผู้ใช้คนนั้นใน production
2. **การแยกการตั้งค่า:** คุณสามารถแก้ไขการตั้งค่า auth (เช่น เทมเพลตอีเมล การตั้งค่าโทเค็น) ภายในบรานช์ได้โดยไม่กระทบ parent branch
3. **การแยก endpoint:** แต่ละบรานช์จะได้รับ Auth API URL เฉพาะของตัวเอง โทเค็นที่ออกในบรานช์หนึ่งจะใช้กับอีกบรานช์ไม่ได้

```
Production Branch              Preview Branch
├── New user: alice@co.com     ├── New user: test@co.com
├── Alice's sessions           ├── Test user's sessions
├── Config: email with links   ├── Config: testing email codes
└── ep-abc123.neonauth...      └── ep-xyz789.neonauth...
    (production endpoint)          (preview endpoint)
```

**หมายเหตุ:** Managed Better Auth ทำงานกับฐานข้อมูล **default** ของบรานช์ (โดยทั่วไปคือ `neondb`) และ read-write endpoint เท่านั้น คุณไม่สามารถใช้ Managed Better Auth กับฐานข้อมูลอื่นภายในบรานช์เดียวกันได้ ซึ่งสอดคล้องกับรูปแบบที่เราแนะนำคือหนึ่งฐานข้อมูลต่อหนึ่งบรานช์

## รายละเอียดการจัดการเซสชัน

เซสชันจะไม่ถ่ายโอนข้ามบรานช์ หากคุณเข้าสู่ระบบในแอป production แล้วไปยัง staging environment:

1. _record_ ของเซสชันจะมีอยู่ในฐานข้อมูล staging (หากถูกสร้างขึ้นก่อนที่จะมีการแตกบรานช์)
2. อย่างไรก็ตาม _cookie_ ในเบราว์เซอร์ของคุณถูกจำกัดขอบเขตไว้กับโดเมน production
3. ดังนั้น คุณจะต้องเข้าสู่ระบบอีกครั้งใน staging environment

การแยกนี้เป็นพฤติกรรมที่ตั้งใจไว้ และช่วยป้องกันปัญหาด้านความปลอดภัย เช่น เซสชันทำงานข้ามสภาพแวดล้อมโดยไม่ตั้งใจ หรือการกระทำระหว่างการทดสอบส่งผลกระทบต่อผู้ใช้ production

## กรณีใช้งานทั่วไป

การแยกบรานช์นี้รองรับเวิร์กโฟลว์ที่มีประโยชน์หลายรูปแบบสำหรับนักพัฒนา ทีม QA และผู้จัดการผลิตภัณฑ์

### 1. การแยกสภาพแวดล้อมของนักพัฒนา

ในสภาพแวดล้อมการทำงานเป็นทีม นักพัฒนามักรบกวนงานกันเมื่อใช้ฐานข้อมูล development ชุดเดียวร่วมกัน เมื่อใช้ branching นักพัฒนาแต่ละคนสามารถมี instance ของตัวเองได้:

```bash filename="Terminal"
# Alice and Bob create their own branches
neon branches create --name dev-alice
neon branches create --name dev-bob
```

- **Alice** ทำงานกับโฟลว์ "Delete Account" เธอสามารถลบผู้ใช้และทดสอบโฟลว์ทั้งหมดได้โดยไม่ต้องกังวลว่าจะกระทบผู้อื่น
- **Bob** ทำงานกับ "User Dashboard" รายชื่อผู้ใช้ของเขายังคงอยู่ครบ แม้ว่า Alice กำลังลบผู้ใช้ในสภาพแวดล้อมของเธอ

เนื่องจาก Managed Better Auth เป็นส่วนหนึ่งของฐานข้อมูล Alice และ Bob จึงไม่จำเป็นต้องตั้งค่า auth provider หรือ mock data แยกกัน ทั้งคู่สามารถทำงานแบบขนานได้โดยไม่เกิดความขัดแย้ง

### 2. ทดสอบการตั้งค่า auth อย่างปลอดภัย

สมมติว่าคุณต้องการเพิ่ม Google OAuth ให้กับแอป production แต่ยังไม่แน่ใจว่าการตั้งค่าจะทำงานหรือไม่ แทนที่จะทดสอบโดยตรงใน production ให้สร้างบรานช์:

```bash filename="Terminal"
# Create test branch from production
neon branches create --name test-google-oauth
```

```env filename=".env.local"
# Point your local app to the test branch's Auth URL
VITE_NEON_AUTH_URL=https://ep-test-google-oauth.neonauth.region.aws.neon.tech/neondb/auth
```

จากนั้นตั้งค่า Google OAuth ใน Console ของ test branch และตรวจสอบว่าโฟลว์การเข้าสู่ระบบทำงานภายในเครื่องได้ แอปและผู้ใช้ production ของคุณจะไม่ได้รับผลกระทบโดยสิ้นเชิง เมื่อยืนยันแล้วว่าทำงานได้ ให้ใช้การตั้งค่า OAuth เดียวกันกับ production branch

แนวทางเดียวกันนี้ใช้ได้กับการเปลี่ยนแปลง auth ทุกประเภท เช่น โฟลว์การรีเซ็ตรหัสผ่าน การตั้งค่าการยืนยันอีเมล หรือการทดสอบด้วยข้อมูล production ที่ผ่านการ anonymize แล้ว

### 3. Preview environment สำหรับ pull request

เมื่อสร้างแอปพลิเคชัน full-stack คุณมัก deploy "Preview Deployments" (ด้วย Vercel, Netlify และอื่นๆ) สำหรับ Pull Request ทุกชุด หากไม่มี Auth Branching preview เหล่านี้มักใช้ auth tenant สำหรับ "Staging" ชุดเดียวร่วมกัน ซึ่งทำให้เกิดความขัดแย้งของข้อมูล เช่น นักพัฒนาคนหนึ่งลบผู้ใช้ที่นักพัฒนาอีกคนกำลังใช้ทดสอบ

**เวิร์กโฟลว์:**

คุณสามารถทำขั้นตอนนี้ให้เป็นอัตโนมัติด้วย GitHub Actions เมื่อมีการเปิด PR:

1. สร้าง Neon branch
2. Deploy frontend/backend ของคุณไปยัง preview URL
3. ใส่ **Branch Auth URL** ลงใน environment variable ของ preview deployment
4. ตั้งค่า Redirect URLs ในการตั้งค่า Auth ของบรานช์ให้ชี้ไปยัง preview URL โดยใช้ [Neon API](https://neon.com/docs/reference/api/auth/add-branch-neon-auth-trusted-domain)

เนื่องจากบรานช์มี snapshot ของข้อมูล production อยู่ preview environment จึงพร้อมทำงานได้เต็มรูปแบบทันที คุณสามารถเข้าสู่ระบบด้วยบัญชีทดสอบจริงที่มีอยู่ใน production แต่การกระทำใดๆ ที่เกิดขึ้น (เช่น การเปลี่ยนรหัสผ่าน การอัปเดตโปรไฟล์) จะเกิดขึ้นอย่างแยกจาก production

**เคล็ดลับ:** ดูวิธีทำ branch creation สำหรับ preview environment แบบอัตโนมัติได้ที่ [คู่มือ GitHub Actions](https://neon.com/docs/guides/branching-github-actions)

### 4. การทดสอบโครงสร้าง multi-tenant และ RBAC

สำหรับแอปพลิเคชันที่มี Role-Based Access Control (RBAC) หรือสถาปัตยกรรม multi-tenant ที่ซับซ้อน การทดสอบการเปลี่ยนแปลงสิทธิ์อาจมีความเสี่ยง การตั้งค่าที่ผิดพลาดอาจทำให้ผู้ใช้ถูกล็อกออกจากระบบ หรือทำให้ข้อมูลสำคัญถูกเปิดเผย

**สถานการณ์:** คุณกำลัง refactor นโยบาย RLS เพื่ออนุญาตให้ "Managers" ดูข้อมูล "Department" ได้ แต่ไม่สามารถแก้ไขข้อมูลนั้นได้

**เวิร์กโฟลว์:**

1. สร้างบรานช์ `refactor-rbac`
2. บรานช์นี้มีผู้ใช้ production จริงและ role assignment ที่มีอยู่เดิม
3. แก้ไขนโยบาย RLS ภายในบรานช์
4. คุณสามารถเข้าสู่ระบบในฐานะผู้ใช้ "Manager" และตรวจสอบว่าผู้ใช้สามารถดูได้เฉพาะข้อมูลที่เหมาะสมเท่านั้น
5. หากนโยบายไม่ถูกต้องและคุณเปิดเผยข้อมูลโดยไม่ได้ตั้งใจหรือทำให้ผู้ใช้ถูกล็อกออกจากระบบ **ผลกระทบจะเกิดขึ้นเฉพาะในบรานช์เท่านั้น** ผู้ใช้ production จะไม่ได้รับผลกระทบ

### 5. การ refactor ครั้งใหญ่และ "v2" beta

เมื่อสร้างแอปพลิเคชันใหม่ตั้งแต่ต้น หรือเปิดตัวการอัปเดต "v2" ครั้งใหญ่ คุณมักต้องตรวจสอบระบบใหม่กับข้อมูลผู้ใช้จริงก่อนสลับระบบอย่างเป็นทางการ ในอดีต ขั้นตอนนี้ต้องใช้การ dump ข้อมูลที่ซับซ้อน หรือขอให้ผู้ใช้สมัครใหม่บนเว็บไซต์ beta

ด้วย Managed Better Auth คุณสามารถสร้างสภาพแวดล้อมคู่ขนานที่สมบูรณ์สำหรับเวอร์ชันใหม่ได้ทันที

**เวิร์กโฟลว์:**

1. **แตกบรานช์จาก production:** สร้างบรานช์ชื่อ `v2-beta` จากฐานข้อมูล production หลักของคุณ ขั้นตอนนี้จะ clone สถานะทั้งหมดของแอปพลิเคชัน รวมถึงสคีมา `neon_auth` ที่มี identity ของผู้ใช้ทั้งหมดและรหัสผ่านที่ผ่านการแฮชแล้ว
2. **Deploy v2:** Deploy โค้ดแอปพลิเคชันใหม่ของคุณ (เช่น ไปที่ `beta.myapp.com`) และชี้ไปยัง Auth URL ของบรานช์ `v2-beta`
3. **เข้าสู่ระบบได้อย่างต่อเนื่อง:** ผู้ใช้เดิมสามารถเข้าเว็บไซต์ v2 ใหม่ของคุณและ **เข้าสู่ระบบได้ทันทีด้วย credential ที่มีอยู่เดิม** โดยไม่จำเป็นต้องสมัครใหม่หรือรีเซ็ตรหัสผ่าน

แนวทางนี้ช่วยให้คุณทดสอบการเปลี่ยนแปลงสถาปัตยกรรมครั้งใหญ่ เช่น การเปลี่ยนชื่อคอลัมน์ฐานข้อมูล การเปลี่ยนโครงสร้างตาราง หรือการแก้ไขโฟลว์การยืนยันตัวตนในสภาพแวดล้อมที่ใช้งานจริงได้ แอปพลิเคชัน v1 ของคุณจะไม่ได้รับผลกระทบโดยสิ้นเชิง ขณะที่ v2 beta ให้ประสบการณ์เหมือนเป็นส่วนต่อขยายของแพลตฟอร์มที่พร้อมใช้งานระดับ production

**หมายเหตุ: การแยกข้อมูล**

โปรดจำไว้ว่าเมื่อแตกบรานช์แล้ว สภาพแวดล้อมแต่ละชุดจะแยกออกจากกัน หากผู้ใช้เปลี่ยนรหัสผ่านบนเว็บไซต์ v2 รหัสผ่านจะไม่เปลี่ยนบนเว็บไซต์ v1 และในทางกลับกัน ทำให้เวิร์กโฟลว์นี้เหมาะสำหรับ "Public Betas" หรือ staging environment ก่อนการ cutover ขั้นสุดท้าย

### 6. AI agent และ ephemeral sandbox

AI Agents โดยเฉพาะเอเจนต์ที่ออกแบบมาสำหรับการเขียนโค้ดหรือ QA จำเป็นต้องมีสภาพแวดล้อมที่ปลอดภัยและแยกออกจากกัน เพื่อสร้างโค้ด รัน migration และตรวจสอบฟีเจอร์ ในอดีต การให้เอเจนต์เข้าถึง authentication stack แบบสมบูรณ์ทำได้ซับซ้อน เพราะคุณต้อง mock auth token หรือเสี่ยงต่อการเปิดเผย production user pool

เมื่อใช้ Neon เอเจนต์สามารถ provision "sandbox" ของตัวเองผ่านโปรแกรมได้ เนื่องจาก Managed Better Auth ย้ายไปพร้อมกับข้อมูล บรานช์นี้จึงสร้างบริการ Authentication ที่ทำงานได้จริงและแยกจาก production ขึ้นมาทันที พร้อม user table, session และการตั้งค่าของตัวเอง **บรานช์มอบสภาพแวดล้อมที่ใกล้เคียง production อย่างสมบูรณ์โดยไม่แตะต้องข้อมูลผู้ใช้จริง**

**เวิร์กโฟลว์:**

1. **Provision:** Agent ใช้ Neon API เพื่อสร้าง database branch ใหม่ และได้รับ Auth URL เฉพาะสำหรับสภาพแวดล้อมนั้นทันที
2. **โต้ตอบ:** Agent ใช้เครื่องมืออย่าง Playwright หรือ Puppeteer เพื่อโต้ตอบกับแอปพลิเคชัน สมัครผู้ใช้ใหม่ และดำเนินโฟลว์การเข้าสู่ระบบจริงกับ auth service ของบรานช์
3. **ตรวจสอบ:** Agent รัน test suite เพื่อตรวจสอบว่าโค้ดที่สร้างขึ้นทำงานร่วมกับ database schema, นโยบาย RLS และกฎการยืนยันตัวตนได้อย่างถูกต้อง
4. **รื้อสภาพแวดล้อม:** เมื่องานเสร็จ Agent จะลบบรานช์ เพื่อล้างข้อมูลและ auth state ทั้งหมด

Agent สามารถสร้างสภาพแวดล้อม full-stack (Database + Auth + Compute) ขึ้นมาได้ภายในไม่กี่วินาที และรัน autonomous test loop กับโฟลว์ความปลอดภัยที่ผู้ใช้โต้ตอบจริงได้โดยไม่ต้องตั้งค่าด้วยตนเอง

**สำคัญ:** AI agent ไม่สามารถเข้าสู่ระบบในฐานะผู้ใช้ production จริงภายในบรานช์ได้ แม้ว่า user record จะถูก copy มา แต่ session cookie ที่ใช้งานได้จะถูกจำกัดขอบเขตตามโดเมนและยังคงอยู่กับเบราว์เซอร์ของผู้ใช้ โดยจะไม่ถูกส่งไปยัง URL ของบรานช์ เว้นแต่เอเจนต์จะทราบรหัสผ่านของผู้ใช้อย่างชัดเจน เอเจนต์ต้องดำเนินโฟลว์การสมัครสมาชิกหรือใช้ credential สำหรับการทดสอบที่มีอยู่เดิมเพื่อเข้าสู่ระบบ

เพื่อให้ขั้นตอนนี้คล่องตัวขึ้น ควรพิจารณารักษาผู้ใช้สำหรับการทดสอบโดยเฉพาะที่มี credential ซึ่งทราบอยู่แล้วไว้ในฐานข้อมูล production ของคุณ record เหล่านี้จะถูก clone ไปยัง child branch โดยอัตโนมัติระหว่างการสร้างบรานช์ ทำให้เอเจนต์สามารถเข้าสู่ระบบได้ทันทีโดยไม่ต้องดำเนินขั้นตอนการสมัครสมาชิก
