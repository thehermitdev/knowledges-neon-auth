> สรุป: โฟลว์การยืนยันตัวตนของ Managed Better Auth ครอบคลุมทุกขั้นตอนตั้งแต่การเรียก SDK ไปจนถึง HTTP-only session cookie, การออก JWT และการเขียนข้อมูลลงในสคีมา neon_auth รวมถึงการเข้าสู่ระบบด้วยอีเมล การสมัครสมาชิก และ OAuth provider เช่น Google และ GitHub ใช้หน้านี้เพื่อทำความเข้าใจสิ่งที่เกิดขึ้นเบื้องหลังระหว่างการเข้าสู่ระบบ ดีบักปัญหาเกี่ยวกับเซสชันหรือโทเค็น หรือเชื่อม `auth.uid()` เข้ากับนโยบาย Row-Level Security ผ่าน Data API สถานะการยืนยันตัวตนทั้งหมดจะถูกบันทึกลงในฐานข้อมูล Neon ของคุณโดยตรงโดยไม่มีความล่าช้าจากการซิงก์ และแต่ละบรานช์จะมีข้อมูลการยืนยันตัวตนที่แยกออกจากกัน

# โฟลว์การยืนยันตัวตน

ทำความเข้าใจกระบวนการเข้าสู่ระบบและสมัครสมาชิกทั้งหมด

**หมายเหตุ: Beta**

**Managed Better Auth** อยู่ในสถานะ Beta คุณสามารถส่งความคิดเห็นผ่าน [Discord](https://discord.gg/92vNTzKDGp) หรือผ่าน [Neon Console](https://console.neon.tech/app/projects?modal=feedback)

คู่มือนี้อธิบายโฟลว์การยืนยันตัวตน ตั้งแต่การเรียก SDK ไปจนถึงการสร้างเซสชันว่ากระบวนการเข้าสู่ระบบทำงานอย่างไร

**หมายเหตุ:** โดยค่าเริ่มต้น ทุกคนสามารถสมัครสมาชิกแอปพลิเคชันของคุณได้ การรองรับการจำกัดการสมัครสมาชิกกำลังจะเพิ่มเข้ามาเร็วๆ นี้ ในระหว่างนี้ ควรพิจารณาเพิ่มขั้นตอนการยืนยันโดยเปิดใช้งาน [การยืนยันอีเมล](https://neon.com/docs/auth/guides/email-verification) ผ่านลิงก์ยืนยันหรือรหัสยืนยัน

## ภาพรวมสถาปัตยกรรม

Managed Better Auth คือบริการ REST API ที่มีการจัดการให้ ซึ่งสร้างบน Better Auth และเชื่อมต่อกับฐานข้อมูล Neon ของคุณโดยตรง คุณใช้ SDK ภายในแอปพลิเคชันและตั้งค่าต่างๆ ผ่าน Console โดยไม่มีเซิร์ฟเวอร์ที่ต้องจัดการเอง

```
Your App (SDK)
    ↓ HTTP requests
Managed Better Auth Service (REST API)
    ↓ connects to database
Your Neon Database (neon_auth schema)
```

ข้อมูลการยืนยันตัวตนทั้งหมด (ผู้ใช้ เซสชัน และการตั้งค่า OAuth) อยู่ในสคีมา `neon_auth` ของฐานข้อมูลคุณ คุณสามารถสืบค้นตารางเหล่านี้ได้โดยตรงด้วย SQL เพื่อใช้สำหรับการดีบัก การวิเคราะห์ข้อมูล หรือโลจิกแบบกำหนดเอง

## โฟลว์การเข้าสู่ระบบแบบสมบูรณ์

ต่อไปนี้คือสิ่งที่เกิดขึ้นเมื่อผู้ใช้เข้าสู่ระบบ ตั้งแต่โค้ดของคุณไปจนถึงฐานข้อมูล:

## ผู้ใช้เข้าสู่ระบบ

แอปพลิเคชันของคุณเรียกเมธอดเข้าสู่ระบบของ SDK:

```typescript
const { data, error } = await client.auth.signIn.email({
  email: 'user@example.com',
  password: 'password',
});
```

SDK ส่งคำขอ POST ไปยัง `{NEON_AUTH_URL}/auth/sign-in/email` บริการ Auth จะตรวจสอบ credential กับ `neon_auth.account` สร้างเซสชันใน `neon_auth.session` และส่ง session cookie กลับมาพร้อมข้อมูลผู้ใช้

**Response ที่คุณได้รับ:**

```typescript
{
  data: {
    session: {
      access_token: "eyJhbGc...",  // JWT token
      expires_at: 1763848395,
      // ... other session fields
    },
    user: {
      id: "dc42fa70-09a7-4038-a3bb-f61dda854910",
      email: "user@example.com",
      emailVerified: true,
      // ... other user fields
    }
  }
}
```

## มีการตั้งค่า session cookie

บริการ Auth จะตั้งค่า HTTP-only cookie (`__Secure-neonauth.session_token`) ในเบราว์เซอร์ของคุณ cookie นี้:

- มี session token แบบ opaque อยู่ภายใน (ไม่ใช่ JWT)
- ถูกส่งไปกับทุก request ที่ส่งไปยัง Auth API โดยอัตโนมัติ
- มีความปลอดภัย (เฉพาะ HTTPS, HttpOnly, SameSite=None)
- ถูกจัดการทั้งหมดโดย SDK คุณไม่จำเป็นต้องจัดการ cookie นี้เอง

**ดูได้ที่ไหน:** เปิด DevTools → Application → Cookies → มองหา `__Secure-neonauth.session_token`

## มีการดึง JWT token

SDK จะดึง JWT token โดยอัตโนมัติและจัดเก็บไว้ใน `session.access_token` คุณไม่จำเป็นต้องเรียก `/auth/token` แยกต่างหาก เพราะ SDK จะจัดการขั้นตอนนี้ให้เบื้องหลัง

**ข้อมูลที่อยู่ใน JWT:**

```json
{
  "sub": "dc42fa70-09a7-4038-a3bb-f61dda854910", // User ID
  "email": "user@example.com",
  "role": "authenticated",
  "exp": 1763848395, // Expiration timestamp
  "iat": 1763847495 // Issued at timestamp
}
```

claim `sub` จะมี user ID จาก `neon_auth.user.id` ซึ่งเป็นค่าที่นโยบาย Row Level Security ใช้เพื่อระบุผู้ใช้ปัจจุบัน

## ใช้ JWT สำหรับการสืบค้นฐานข้อมูล

เมื่อคุณสืบค้นฐานข้อมูลผ่าน Data API ตัว SDK จะใส่ JWT ลงในเฮดเดอร์ `Authorization` โดยอัตโนมัติ:

```typescript
// JWT is automatically included in Authorization header
const { data } = await client.from('posts').select('*');
```

**สิ่งที่เกิดขึ้น:**

1. SDK ดึง JWT จาก `session.access_token`
2. เพิ่มเฮดเดอร์ `Authorization: Bearer <jwt-token>`
3. Data API ตรวจสอบลายเซ็น JWT โดยใช้ JWKS public keys
4. Data API ดึง user ID จาก JWT และทำให้ค่านี้พร้อมใช้งานสำหรับนโยบาย RLS
5. Query ของคุณทำงานภายใต้บริบทของผู้ใช้ที่ผ่านการยืนยันตัวตนแล้ว

## โฟลว์การสมัครสมาชิก

โฟลว์การสมัครสมาชิกจะสร้างผู้ใช้ใหม่:

```typescript
const { data, error } = await client.auth.signUp.email({
  email: 'newuser@example.com',
  password: 'securepassword',
  name: 'New User',
});
```

SDK ส่งคำขอ POST ไปยัง `{NEON_AUTH_URL}/auth/sign-up/email` บริการ Auth จะสร้างแถวใหม่ใน `neon_auth.user` จัดเก็บ credential ที่ผ่านการแฮชแล้วไว้ใน `neon_auth.account` และส่งข้อมูลผู้ใช้กลับมา หากกำหนดให้ต้องยืนยันอีเมล ระบบจะสร้าง verification token ใน `neon_auth.verification` และอาจชะลอการสร้างเซสชันจนกว่าจะยืนยันเสร็จ

**หมายเหตุ:** โดยค่าเริ่มต้น ทุกคนสามารถสมัครสมาชิกแอปพลิเคชันของคุณได้ หากต้องการเพิ่มชั้นการยืนยันเพิ่มเติม ให้เปิดใช้งานการยืนยันอีเมล (ดู [การยืนยันอีเมล](https://neon.com/docs/auth/guides/email-verification)) ระบบจำกัดการสมัครสมาชิกแบบ built-in กำลังจะเพิ่มเข้ามาเร็วๆ นี้

## โฟลว์ OAuth

การยืนยันตัวตนด้วย OAuth (Google, GitHub, Vercel และอื่นๆ):

```typescript
await client.auth.signIn.social({
  provider: 'google',
  callbackURL: 'http://localhost:3000/auth/callback',
});
```

SDK จะ redirect ไปยัง OAuth provider หลังจากผู้ใช้ยืนยันตัวตนแล้ว provider จะ redirect กลับมาพร้อม authorization code จากนั้น SDK จะนำ code ไปแลกเป็น access token แล้วบริการ Auth จะสร้างหรืออัปเดตผู้ใช้ใน `neon_auth.user` จัดเก็บ OAuth token ไว้ใน `neon_auth.account` และสร้างเซสชัน

## ฐานข้อมูลเป็น source of truth

Managed Better Auth จัดเก็บข้อมูลทั้งหมดไว้ในสคีมา `neon_auth` ของฐานข้อมูลคุณ:

- การเปลี่ยนแปลงมีผลทันที (ไม่มีความล่าช้าจากการซิงก์)
- สืบค้นข้อมูลการยืนยันตัวตนได้โดยตรงด้วย SQL
- แต่ละบรานช์มีข้อมูลการยืนยันตัวตนที่แยกออกจากกัน
- คุณเป็นเจ้าของข้อมูลของคุณ

```sql
SELECT id, email, "emailVerified", "createdAt"
FROM neon_auth.user
ORDER BY "createdAt" DESC;
```

## การผสานรวม Data API

เมื่อคุณเปิดใช้งาน [Data API](https://neon.com/docs/data-api/get-started) JWT token จาก Managed Better Auth จะได้รับการตรวจสอบโดยอัตโนมัติ มี helper function สองตัวที่ทำให้ user ID พร้อมใช้งานสำหรับนโยบาย RLS ให้เลือกใช้ตัวที่ตรงกับชนิดข้อมูลของคอลัมน์:

- `auth.user_id()`: คืนค่า `sub` เป็น `text`
- `auth.uid()`: คืนค่า `sub` เป็น `uuid` (คืนค่า `NULL` หาก `sub` ไม่ใช่ UUID ที่ถูกต้อง)

Data API ยังทำงานร่วมกับ [ผู้ให้บริการยืนยันตัวตนรายอื่น](https://neon.com/docs/data-api/custom-authentication-providers) ที่ออก JWT เช่น Auth0, Clerk และ Firebase ได้ด้วย

**ตัวอย่างนโยบาย RLS:**

```sql
CREATE POLICY "Users can view own posts"
ON posts FOR SELECT TO authenticated
USING (user_id = auth.user_id());
```

**เรียนรู้เพิ่มเติมเกี่ยวกับการรักษาความปลอดภัยของข้อมูล:**

- [Row-Level Security กับ Neon](https://neon.com/docs/guides/row-level-security)
- [ทำให้ RLS ง่ายขึ้นด้วย Drizzle](https://neon.com/docs/guides/rls-drizzle)
